## 1. CEO 질문 3개에 대한 답

### Q1. 의뢰자가 리워드광고를 다랜드 *안에서* 관리하게 하고 싶은 게 맞나?

**맞다. 세 가지 근거.**

1. **홈 랜딩 5단계 메뉴의 정식 항목** — `f2767a46-…png`, `8a80071d-…png`: 회원가입 → 입금 → 지출 → 출금 → **리워드광고**. 다른 네 개와 같은 급으로 그려져 있다. 외부 툴 링크가 아니다.
2. **하단 탭바에 "리워드" 탭 상주** — `487ec707-…png`, `cd9c4af8-…png`, `ef434a4c-…png`: 홈·입금·지출·출금·**리워드** 5탭. 리워드 화면 안에 "광고 내역 확인 / 지급 내역 확인" 버튼이 있다 = 앱 안에서 내역 조회까지 끝내겠다는 뜻.
3. **관리자 승인 절차를 의뢰자가 스스로 그렸다** — `3a245f2c-…png` 12단계 "광고가 승인 후 송출됩니다", 13단계 "광고 송출 중 · 송출 진행률 65%", 14단계 "광고 성과 분석", 15단계 "리워드 지급 및 적립". 승인·송출·성과·지급을 누군가 관리한다는 전제가 깔려 있고, 그 누군가가 관리자다.

덧붙여 이용약관 제9조 (`26fd2edf-…png`, 현재 `terms/page.tsx` 167행에도 반영됨) "회사는 회원이 설정한 조건에 따라 SNS 통해 리워드 광고를 발송" — 발송 주체가 **회사**다. 회사가 발송하려면 회사(관리자)가 캠페인을 보고 승인하는 화면이 있어야 한다.

### Q2. "리워드"가 정확히 뭔가?

**한 문장:** 광고주(입금 10만원 이상 회원)가 자기 다랜드 포인트 잔액에서 떼어, 자기 광고를 보고 다랜드에 새로 가입한 회원에게 1인당 정액(1만·10만·100만·1천만P 중 택1)을 주는 **가입 보상**이며, 이유는 **회원 유치**다.

시안 근거:
- 금액 프리셋: `487ec707-…png` (1만/10만/1백만/1천만원), `ef434a4c-…png` (10만P/100만P/1,000만P/수기), `3a245f2c-…png` 3단계 "광고주가 지급할 1인 리워드 금액"
- 지급 대상: `cd9c4af8-…png` 광고 종류 ① "신규 회원 가입 리워드 — 가입 시 리워드를 지급", ② "기존사이트 회원DB 연동 — 기존회원에 리워드 지급"
- 광고주 자격: `a6e21f75-…png` 붉은 박스 "광고주가 되려면 10만원 이상을 입금하셔야 합니다"
- 지급 트리거: `3a245f2c-…png` 15단계 "가입 회원에게 100만P 지급 완료"

**의뢰자가 "리워드"에 붙여 놓은 두 번째·세 번째 의미** (이건 리워드가 아니라 광고주 *수익* 주장이라 따로 다룬다 — §2, §7):
- "광고주가 10만P 지급하면 Model A로 12만P 광고주에게 지급" (`ef434a4c-…png`, `8e6a37d7-…png`)
- "유치한 회원이 지출할 때마다 5%를 평생 광고주에게 적립" (`ef434a4c-…png`, `1ed1274c-…png` 광고 내용 3))

### Q3. 지출 항목에 "리워드(보상)광고"가 들어간 것 = 광고비를 120%로 증액하고 싶은 건가?

**의뢰자 의도는 "예"다. 그러나 그대로 구현하면 안 되고, 시안 스스로가 갈라 놓은 두 갈래로 나누면 정직하게 살릴 수 있다.**

의뢰자 의도 근거:
- `38188e93-…png` 지출하기: 항목 8종 (a.원자재 b.인건비 c.임대료 d.공과금 e.세금 f.대출상환 g.생활비 **+ 리워드(보상)광고**) → 결제방법 (카드+OCR / 다랜드 포인트) → "100% 차감 → 120% 증액 적립 (Model A)". 리워드광고를 임대료와 같은 줄에 놓았다 = 같은 120% 규칙을 태우고 싶다.
- `8e6a37d7-…png` 6단계: "1백만원 입금 → 10만P 분배 → 총량유지 모드 120% 적립 (12만P)". 분배 자체를 120% 지출로 본다.
- `11e6bdd6-…png`: 지출 종류 표에 "g. 리워드(광고)광고" 와 "g. 투자금"이 나란히 있다 (라벨 g 중복 = 시안 오타).

왜 그대로는 안 되나:
- 현재 지출 엔진(`spend/register`)은 `next = current - spendAmount + 120%` 로 순 +20%를 준다. 여기에 "리워드 분배"를 태우면 광고주 -10만 +12만, 신규회원 +10만 → 캠페인 1건당 **12만P가 무에서 생성**된다. PR #34 (출금 100%, 120%는 재지출 시에만) 결정의 정반대.
- 부칙 제1조 (PR #35, `3f754982-…png` 부칙 제4조 대응) "투자금은 총량유지 미적용" — 광고주 입금은 실질적으로 광고 투자금이다. 여기에 120%를 붙이면 부칙과도 충돌한다.

**정직한 분리안** (시안 10단계 `3a245f2c-…png` "100만P 지출 → PG + 채널광고비 = 1백만 지출"에서 의뢰자도 이미 두 요소를 나눠 놨다):

| 광고비 갈래 | 실체 | 결제 수단 | 적립 규칙 | 지출 항목 |
|---|---|---|---|---|
| ① 외부 광고비 (채널 광고비·PG 수수료·영상 제작비) | 돈이 다랜드 **밖**으로 나감 | 카드 → OCR | **120%** (기존 카드지출과 동일, PR #34 정합) | `reward-ad` 신규 항목 |
| ② 리워드 포인트 이전 (신규회원에게 주는 정액) | 다랜드 **안**에서 광고주→회원 이동 | 포인트 (에스크로) | **100% 제로섬**, 증액 없음 | 지출 항목 아님 → `rewardPayouts` 원장 |

이렇게 하면 "지출 항목: 리워드(보상)광고"는 살고 (①), 무에서 생성은 막힌다 (②). 의뢰자에게는 "광고비 중 실제로 카드 긁은 부분은 다른 지출과 똑같이 120%, 회원에게 준 포인트는 회원 것이 됐으니 광고주에게 되돌아오지 않는다"로 설명한다.

## 2. 리워드 흐름의 정직한 정의

### 2.1 원칙 세 줄

1. **무에서 포인트 생성 금지.** 모든 포인트 증가는 (a) 입금 (b) 카드 실지출 OCR 검증 후 120% (c) 다른 회원 잔액에서 온 이전, 셋 중 하나에서만.
2. **리워드 = 이전.** 광고주 잔액 -X, 신규회원 잔액 +X. 합계 변화 0.
3. **120%는 재지출에만.** 리워드 받은 신규회원이 그 포인트를 카드 지출로 쓰고 OCR이 잡으면 그때 120% — 이미 있는 규칙이고 리워드 때문에 새로 생기는 건 없다.

### 2.2 원장 흐름 (P0 구현 대상)

```
[광고주]                              [캠페인 에스크로]                      [신규회원]
totalPoints −budget ─(제출: 잠금)─▶ 광고주 users.lockedPoints +budget
                                     (= rewardCampaigns.budgetLocked 합계)
                                        │
                                        ├─(가입+조건 충족: 리딤)─▶ lockedPoints −unit → 회원 totalPoints +unit
                                        │   rewardPayouts 1건 생성 (payout)
                                        │   transactions type=reward_in (회원) / reward_out (광고주)
                                        │
                                        └─(거절·종료·취소)─▶ lockedPoints −잔여 → 광고주 totalPoints +잔여 (refund)
```

세 이동 어디서도 `Σ totalPoints + Σ lockedPoints` 는 변하지 않는다 (잠금·리딤·반환 전부 좌우 합 0). `lockedPoints` 는 출금 가능 잔액에서 제외된다 (§7.4).

- 예산 잠금 시점: 캠페인 **제출** 시 (승인 전에 잠가야 승인 후 잔액 부족으로 지급 실패하는 일이 없다). 거절되면 즉시 전액 반환.
- 지급 조건 (P0): 캠페인 코드/링크로 가입 + 이메일 인증 + 1인 1회 (`rewardPayouts/{inviteeUid}` 문서 ID로 멱등). 기존 `inviteRedemptions/{inviteeUid}` 패턴 유지.
- 지급 조건 (P1 추가): 첫 입금 1만P 이상 완료 후 지급 — 시안 `a6e21f75-…png` "일반회원은 1만원 이상 입금되어야 회원 신청 및 가입 가능"과 맞고, 봇 가입 방어에도 필요. **P0에서 조건 없이 가입 즉시 지급하면 다계정 어뷰징으로 광고주 예산이 증발한다** — 강체크 검토 항목 §7-1.

### 2.3 광고주에게 돌아가는 것 (정직 버전)

| 의뢰자 표현 | 정직 대체 | 상태 |
|---|---|---|
| "10만P 지급하면 12만P 광고주에게" | 돌아오지 않는다. 광고주가 얻는 건 **회원 1명**. 회원이 카드 지출하면 그 회원이 120% 받는다. | 문구 반려 |
| "유치 회원 지출의 5%를 평생 광고주에게" | 엔진에 이미 `advertiserReward` 필드가 있다 (`spend/register` 109행, `nl.advertiser.advertiserReward`). **재원을 어디서 댈지**가 문제: 20% 증액분 안에서 나누느냐(소비자 115+광고주 5), 밖에서 더하느냐(플랫폼 부채 125%). | CEO 결정 §8-3, P2 |
| "입금하면 120%" (`94c74723-…png` 하단 "입금하신 금액은 120% 증액되어 적립") | 입금은 100%. 현재 `deposit` API도 100%다. 문구만 시안에 남아 있음. | 문구 반려 |
| "출금 100% + 120% 재충전" | PR #34 문구 그대로 유지 ("120%는 재지출 시") | 유지 |

| **입금** | 오늘 입금 P / 확인 대기 건 / CMS 등록 회원 / 이번 달 총 입금 | 회원·금액·방법(계좌/CMS)·입금자명·요청시각·상태 | **입금 확인(승인)**, 반려, CMS 등록 확인 | P1 |
| **지출·OCR** | 오늘 지출 건 / 120% 발행 P / OCR 미검증 건 / 수동분할 대기(10억 초과) | 회원·항목·금액·결제수단·OCR 상태·적립 P | OCR 영수증 보기, 검증/반려, 수동 분할 처리 | P1 |
| **출금** | (기존) 대기 / 오늘 승인 / 반려 / 총 출금 | 기존 `AdminWithdrawal` 그대로 | 승인·반려 (기존 API) | P0 (이관만) |
| **리워드광고** | 승인 대기 / 진행 중 / 오늘 지급 P / 잠긴 예산 총합 | 캠페인 ID·광고주·종류·1인 금액·인원·예산(잠김/지급/잔여)·채널·상태·제출일 | **승인 / 거절(사유) / 일시정지 / 종료(잔여 반환)**, 송출 기록, 지급내역 탭, 성과 탭 (도달·가입·지급·전환율) | P0 |
| **총량 모니터** | Σ회원 잔액 / Σ입금 - Σ출금 / Σ120% 증액 발행 / Σ리워드 잠김 | 일자별 총량 스냅샷 + 불일치 경고 | 스냅샷 생성, 불일치 상세 | P0 (기본) / P1 (일별) |
| **공지** | 게시 중 / 예약 / 조회 / 마지막 발행 | 제목·대상(전체/광고주/기업)·게시일·상태 | 작성·게시·내리기 | P1 |
| **설정** | — | 분배 모드(기존 auto/manual), 광고주 자격 하한(10만), 리워드 프리셋, 캠페인 최소 인원, 관리자 이메일 allowlist | 저장 (감사 로그) | P0 (이관) / P1 (확장) |

총량 모니터 정합식: `Σ users.totalPoints + Σ users.lockedPoints(캠페인 에스크로 잠김) == Σ deposit − Σ withdraw(completed) + Σ spend.bonus − Σ spend.principal(포인트결제분) + 0(리워드는 제로섬) + 베타 조정(§8-6, 기존 inviteRedemptions 분)`. 좌변에 에스크로 항을 넣는 이유: 제출 시 `totalPoints → lockedPoints` 로 옮기므로 `totalPoints` 만 보면 잠긴 예산만큼 총량이 줄어든 것처럼 보인다. 검산: `Σ users.lockedPoints == Σ rewardCampaigns(status ∈ live·approved·paused·pending_review).budgetLocked − budgetPaid − budgetRefunded`. 이 식이 안 맞으면 어딘가에서 무에서 생성됐다는 신호다. 지금 코드로 돌리면 `inviteRedemptions` 만큼 안 맞을 것 — 그게 P0-1의 증거 화면이 되고, P0-1 이후엔 그 차이가 "베타 조정" 항목으로 분리 표기된다.

```ts
// users/{uid}  (기존 컬렉션에 필드 추가)                          [P0]

// rewardCampaigns/{campaignId}                                  [P0]
{

  headcount: number,                               // 모집 인원
  budgetLocked: number,                            // unitAmount × headcount, 제출 시 잠금

  stats: { reach, signups, paid, conversionRate }, // P1
  createdAt, submittedAt, reviewedAt, reviewedBy, endedAt
}

// rewardPayouts/{inviteeUid}      (1인 1회 멱등)                 [P0]
```
