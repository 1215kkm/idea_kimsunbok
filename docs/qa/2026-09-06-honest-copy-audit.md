## 1. 정직 문구 감사표

판정 기준
- **제거**: 무에서 생성·광고주 수익·입금 증액·미구현 배분을 약속. 대체 없이 삭제.
- **치환**: 의도(회원 유치·가입 보상)는 살리되 제로섬 표기로. 대체 문구는 "가입 시 N P 지급", "광고주 예산에서 회원에게 이전" 계열만.
- **유지**: PR #34 정합(카드 실지출 → OCR → 120%) 또는 구체 약속 없음.

`N` = 캠페인 1인당 금액(`unitAmount`), 화면에선 실제 숫자로 바인딩.

## 2. 원장 구멍 목록

강개발 규칙(감사 시점 diff 0, 설계 기준): 제출 시 `users.totalPoints −unit×headcount` → `users.lockedPoints +`. 리딤 시 `lockedPoints −unit`, 회원 `totalPoints +unit`. 거절·종료 시 잔여 → `totalPoints` 반환. 총량 좌변 = Σ(totalPoints + lockedPoints).

- 증상: `auth/post-signup/route.ts:58-70` 외에 **상시 호출 가능한** `POST /api/invite/redeem` 이 별도로 있다. P0-1 이 post-signup 만 새 서비스로 바꾸면 이 라우트가 계속 `redeemInviteCode` → 광고주 `+advertiserNetGain` 을 무에서 생성한다.

### #2 [치명] 이메일 인증 없는 즉시 지급 + 다계정 — `auth/post-signup/route.ts:58`, `lib/server/auth.ts:34`
- 증상: `requireAuth` 가 `emailVerified` 를 돌려주지만 아무 데서도 안 본다. `AuthContext.tsx:78-91` 은 `createUserWithEmailAndPassword` 직후 post-signup 호출, `sendEmailVerification` 호출 자체가 없다. 기획서 P0 조건 "가입 + 이메일 인증" 은 **코드에 아직 없다**.
- 예산 소진 속도 (계산): Firebase REST signUp 1건 ≈ 200~400ms. 100만P × 100명 = 1억P 캠페인 → 스크립트 100계정 ≈ **30~40초**에 전액 소진. 이메일 인증을 붙여도 Gmail `+태그`·점(dot) 변형은 Firebase 에서 **전부 다른 계정**이라 1개 메일함으로 무제한. 계정마다 베타 100만P 시드(`post-signup:17`)까지 얹힌다.
- 탈퇴 루프: 지급 → (P1 환불 API 생기면) 탈퇴 전액 환불 → 재가입 = 광고주 돈 현금화 루프. #4 참조.
- P1 "첫 입금 1만P" 전 임시 방어 (비용 순, 전부 서버 측):
  1. `decoded.email_verified === true` 아니면 리딤 보류 — `auth.ts` 에 이미 값 있음, 5줄.
  2. 이메일 정규화 키: 소문자 + gmail 계열 점 제거 + `+` 이후 제거 → `rewardPayoutKeys/{sha256(normalizedEmail)}` 로 2차 멱등 (uid 재생성·탈퇴 재가입도 잡힘).
  3. 일회용 메일 도메인 차단 목록 (`settings/system.blockedEmailDomains`, 관리자 설정).
  4. **캠페인당 일일 지급 상한** `dailyCap = min(headcount, settings.rewardDailyCap(기본 10))` — 하루 소진 상한 = 광고주 최대 손실 상한. 초과분은 `rewardPayouts.status="pending"` 으로 대기.
  5. IP 상한: `x-forwarded-for` 첫 값 기준 캠페인당 24h 3건. Vercel 은 헤더 신뢰 가능.
  6. 24h 지연 지급 + 관리자 일괄 승인·역전(`reversed`) — 어뷰징 발견 시 되돌릴 시간.
  7. Firebase App Check(reCAPTCHA Enterprise) 가입 폼 — 스크립트 가입 비용 상승.
  권고 조합: 1+2+4 는 P0 필수, 5+6 은 P0 권장, 3+7 은 P1.

### #3 [주의] 동시 리딤 경쟁 — Firestore 트랜잭션은 **조건부로** 충분
- 충분한 조건: (a) 캠페인 문서와 광고주 `users` 문서를 **트랜잭션 안에서 `tx.get`** 하고 (b) `budgetLocked − budgetPaid ≥ unit` 및 `lockedPoints ≥ unit` 을 **읽은 값으로** 검사한 뒤 (c) `rewardPayouts/{uid}` 는 `tx.create`(존재 시 실패). Firestore 는 낙관적 동시성이라 두 트랜잭션 중 하나는 재시도 후 (b) 에서 실패 → 정확히 1건만 지급.
- 뚫리는 구현: `FieldValue.increment(-unit)` 만 쓰고 잔여 검사를 트랜잭션 밖에서 하거나, `tx.set(..., {merge:true})` 로 멱등 문서를 쓰는 경우(기존 `invite-service.ts:150-159` 가 set merge 패턴 — 새 코드에서는 `create` 로).
- 운영 리스크: 인기 캠페인 100명 동시 가입 → 같은 캠페인·광고주 문서에 쓰기 집중 → ABORTED 재시도 폭증. post-signup 은 리딤 실패를 `inviteError` 로 삼키고 가입은 성공시키므로(`:63-69`) 회원은 **보상 없이 가입 완료**, UI 에 재시도 버튼 없음.
- 우회안: 리딤 실패 시 `rewardPayouts/{uid}` 를 `status:"pending"` 으로 먼저 예약(create) 하고 실제 이전은 재시도(Cloud Function 또는 다음 로그인 시 `reward/claim`). 대시보드에 "지급 대기 N P" 표시.

### #4 [치명] 탈퇴 — `app/src/app/account/leave/page.tsx:56-66`
- 증상: Firebase 모드에서 **서버 호출이 없다.** `signOut()` 만 하고 `step="complete"` → "환불 예정 금액 N원, 1~2일 내 입금" 을 보여준다. 계정·`users` 문서·잔액 전부 그대로. 화면은 "전액 환불" 을 약속하고 시스템은 아무것도 안 한다.
- 리워드와의 충돌 (P1 에서 진짜 탈퇴 API 만들 때):
  - 광고주 탈퇴: `lockedPoints` 를 환불액에 포함하면 진행 중 캠페인 예산이 사라지고(회원 지급 실패), 제외하면 광고주 돈이 증발. **순서**: 진행 캠페인 전부 `ended` + 잔여 반환 → 그 다음 환불 계산.
  - 신규회원 탈퇴: 리워드 받은 직후 탈퇴·환불 = 광고주 예산 현금화. 리워드 수령 후 30일 환불 잠금, 또는 잔액이 리워드 원금 이하일 땐 `rewardPayouts.amount` 만큼 `reversed` 후 광고주에게 반환.
  - Firebase Auth 삭제 후 재가입 = 새 uid → `rewardPayouts/{newUid}` 신규 → 재수령. #2-2 이메일 정규화 키가 막는다. 탈퇴 시 `rewardPayoutKeys` 문서는 **삭제하지 않는다**(툼스톤).
- 우회안 (P0): 탈퇴 화면에 "(베타) 환불 절차는 정식 출시 시 제공" 단서 + 1.12 문구 정리. 실제 API 는 P1-2 입금확인과 같은 묶음으로.

### #9 [주의] 지급 역전(`reversed`)의 총량 깨짐
- 증상: 어뷰징 회원이 리워드를 이미 지출·출금한 뒤 관리자가 `reversed` 하면 회원 잔액 < unit → 광고주에게 전액 반환하면 무에서 생성, 부분 반환하면 광고주 손실.

## 3. 5% 배분 시뮬레이션 (P2-2 재료)

가정: 유치 회원 1,000명 · 1인 월 카드지출 50만원(전부 OCR 인식) · 12개월 · 리워드로 받은 포인트의 재지출 2차 효과는 제외(보수적). 5% 는 `nonlinear-engine.ts:65 advertiserRate=0.05` 대로 **지출액 기준**.

- 회원 총 지출 = 1,000 × 500,000 × 12 = **60억원**
- 현행(120%, 5% 미지급) 플랫폼 발행 = 60억 × 20% = **12억** (월 1억)

| 개월 | 회원 지출 누적 | 현행 발행 (회원 20%) | (가) 20% 안 분할: 회원 15% + 광고주 5% | (나) 밖에서 추가: 회원 20% + 광고주 5% | (나) − 현행 |
|---|---|---|---|---|---|
| 1 | 5억 | 1.00억 | 0.75 + 0.25 = **1.00억** | 1.00 + 0.25 = **1.25억** | +0.25억 |
| 3 | 15억 | 3.00억 | 2.25 + 0.75 = 3.00억 | 3.00 + 0.75 = 3.75억 | +0.75억 |
| 6 | 30억 | 6.00억 | 4.50 + 1.50 = 6.00억 | 6.00 + 1.50 = 7.50억 | +1.50억 |
| 12 | 60억 | **12.00억** | 9.00 + 3.00 = **12.00억** | 12.00 + 3.00 = **15.00억** | **+3.00억** |

- 광고주 관점(회원 100명 유치 시): 연 3억 × 100/1,000 = **3천만원/년** 수령. 캠페인 비용 100명 × 10만P = 1천만P → 4개월 회수. 이게 의뢰자가 "셀링 포인트" 라 부르는 숫자이고, (가)(나) 어느 쪽이든 광고주 수령액은 같다. 차이는 **누가 내느냐**뿐.
- (가): 플랫폼 부채 증가 0. 대신 "120%" 를 약속한 모든 화면·약관 제7조를 **115%** 로 바꿔야 한다(현재 "120%" 문자열 화면 9개 파일). 회원 가치 −5%p.
- (나): 회원 약속 유지. 플랫폼 발행 +25%(연 12억 → 15억). 현재 플랫폼 실수익원(수수료 실수취)은 **0** 이라 전액 순부채.
- 2차 효과 주의: 발행된 포인트가 다시 카드지출되면 그 지출에도 20%(+5%)가 붙는다. 재지출률 50% 가정 시 12개월 누적 발행은 위 표의 약 1.6배 — 어느 안이든 재원 없이 시행 불가.

**결론 한 줄:** (가)는 부채 0 이지만 "120%" 약속을 전면 115% 로 바꿔야 하고, (나)는 1,000명당 연 3억 순부채가 추가되는데 현재 수익원이 없다 — 재원(수수료·광고 실수익)이 실제로 걷히기 전엔 P2 보류 유지가 맞고, 굳이 앞당기면 (가) + 문구 전면 교체가 유일하게 총량유지와 맞는 안이다.
